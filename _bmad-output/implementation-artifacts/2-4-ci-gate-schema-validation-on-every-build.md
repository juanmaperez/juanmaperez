## Story

As a **maintainer**,  
I want **CI to fail** on invalid markdown content **before deploy**,  
So that **FR17** is a hard gate (mandatory MVP cutover gate per PRD), not a manual local-only check.

---

## Acceptance criteria (from epics)

1. **Given** the deploy workflow `.github/workflows/deploy-astro-pages.yml` (from Story 1.3) and a branch with **all valid** content  
   **When** CI runs on push or PR  
   **Then** the pipeline **passes** — schema-validation step exits 0, `npm run build` exits 0, `actions/deploy-pages` deploys (on main).

2. **Given** the same workflow and a branch where **any** post or project has **invalid frontmatter** (missing required field, wrong type, wrong literal)  
   **When** CI runs  
   **Then** the pipeline **fails at the schema-validation step** with a **readable** Zod / `astro check` error message in the GitHub Actions log (field-level message preferred), **before** the build/deploy steps run.

3. **Given** a PR introducing invalid content  
   **When** the workflow runs  
   **Then** the failed CI status **blocks merge** to main (visible as a failing required check on the PR).

4. **Given** the workflow file after this story  
   **When** read by a maintainer  
   **Then** there is exactly **one** new step (or one extended step) running schema validation **before** `npm run build`, with a clear `name:` referencing FR17.

### Why `npm run check` (not `npm run test:schema`) in CI

- `npm run check` = `astro check`. **Validates ALL real content** in the tree against the Zod schemas. If any of the 9 posts or 5 projects breaks, this fails.
- `npm run test:schema` = `verify-content-schema.mjs`. **Injects invalid fixtures and asserts they fail.** Useful as a local meta-test that the gate works, but tautological in CI: if `npm run check` works on real content, the gate is real.
- CI cost: `npm run check` adds **~3–8s** to a typical Astro 6 run. `test:schema` would add **2× that plus fixture I/O**. Not worth it for the marginal coverage.
- AC2 ("invalid content fails CI") is met by `npm run check` running before `npm run build` — invalid frontmatter would fail at `astro check` first. The dev verification step (running `test:schema` locally) is the proof.

### Edge cases to watch

- **Astro check + `glob-loader` warnings** — Astro emits `[glob-loader] No files found …` if a collection is empty. Currently both collections have content, so no warning. If a future story empties one (unlikely), `astro check` should still **pass** (warnings ≠ errors). Only schema violations fail.
- **Caching** — `actions/setup-node@v4` with `cache: npm` already caches `~/.npm` keyed on `site/package-lock.json`. The `.astro/` build cache is **not** cached across CI runs (and shouldn't be — fresh validation every push is the point of FR17).
- **Working-directory** — Every `run:` step that touches Node tooling **must** include `working-directory: site` (consistent with existing 1.3 steps). Without it, `npm run check` fails because there's no `package.json` at repo root for the site.
- **Concurrency group** — `concurrency: pages` with `cancel-in-progress: true` is already set (Story 1.3). New step inherits this; no change needed.
- **Permissions** — `contents: read`, `pages: write`, `id-token: write` are already declared. `astro check` needs none of these beyond `contents: read`. No permission changes.
- **PRs from forks** — `actions/deploy-pages` is restricted on PRs, but the **build job** (including the new check step) runs on PRs. This means **AC2 is enforced on PRs from branches in the same repo**. Forks may have limited permissions — out of scope to address.
